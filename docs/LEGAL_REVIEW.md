## 1. 🔴 치명

### 1-1. 민감정보 국외 이전 고지가 법정 요건에 미달

**근거**: 개인정보보호법 제28조의8 (국외 이전), 제23조 (민감정보)

건강검진 결과지 **원본 파일 전체**가 미국 Anthropic PBC 로 전송됩니다.
(`src/lib/checkup/extract.ts` — PDF/이미지를 base64 로 인코딩해 API 로 전송)

결과지에는 성명·생년월일·검진기관·전 검사 수치가 인쇄되어 있습니다. 즉
**민감정보와 개인식별정보가 한꺼번에 국외로 나갑니다.**

제28조의8 제2항은 국외 이전 동의를 받을 때 다음을 **모두** 알리도록 정하고 있습니다.

| 고지 항목 | 현재 문안 |
|---|---|
| 이전되는 개인정보 항목 | △ "결과지 파일"로만 — 그 안의 성명·생년월일 등은 언급 없음 |
| 이전받는 국가·시기·방법 | △ "미국"만. 시기·방법 없음 |
| 이전받는 자의 성명·연락처 | △ 상호만. 연락처 없음 |
| 이전받는 자의 이용 목적·보유 기간 | ⚠️ §2-4 참고 — 사실 확인 없이 단정 |
| **거부 권리·방법·거부의 효과** | ❌ "거부해도 직접 입력 가능"이라고만. 거부 방법 없음 |

### 1-2. 처리위탁 수탁자 목록이 통째로 없음

**근거**: 개인정보보호법 제26조, 제30조 제1항 제3호

이 서비스의 개인정보는 전부 외부 인프라 위에 있는데, 처리방침에 수탁자가
**한 곳도 적혀 있지 않습니다.**

| 수탁자 | 위탁 업무 | 처리하는 개인정보 | 코드 근거 |
|---|---|---|---|
| Supabase | DB · 인증 · 파일 저장 | **전부** (계정, 프로필, 모든 건강기록, 결과지 원본) | `src/lib/supabase/*` |
| Vercel(추정) | 애플리케이션 호스팅 | 요청 처리 중 경유하는 전부 | 배포 대상 |
| Anthropic PBC | 결과지 자동 판독 | 결과지 원본 파일 | `src/lib/checkup/extract.ts` |
| 브라우저 푸시 서비스<br>(Google / Apple / Mozilla) | 복약 알림 전달 | 푸시 endpoint, 암호화된 알림 페이로드 | `src/app/api/push/dispatch/route.ts` |
| 식품의약품안전처 | 음식 영양성분 조회 | 검색어만 (식별자 없음) | `src/lib/food/mfds.ts` |

Supabase 와 Vercel 의 리전에 따라 **이것도 국외 이전**입니다. 현재 리전이
정해지지 않았으므로 §4-1 참고.

### 1-3. 개인정보 보호책임자·연락처 미기재

**근거**: 개인정보보호법 제31조, 제30조 제1항 제5호

처리방침에 보호책임자의 성명·직책·연락처가 반드시 있어야 하는데 없습니다.
운영 주체(상호·대표자·주소)도 없습니다. 정보주체가 권리를 행사할 창구 자체가
문서상 존재하지 않습니다.

### 1-4. 이용약관이 사실상 없음

현재 이용약관은 두 문단이고, 그 내용은 "의료기기가 아니다"라는 면책 고지뿐입니다.
계약 관계를 규율하는 조항이 하나도 없습니다.

없는 것: 계약 성립·적용, 계정과 비밀번호 관리 책임, 이용자 금지행위, 서비스
변경·중단, 이용 제한·해지, 손해배상과 면책 범위, 지식재산권 귀속, 데이터
반출(서비스 종료 시), 약관 변경 절차, 준거법·관할.

## 2. 🟠 중대 — 문서에 없는 데이터 흐름

이 절이 이번 검토의 핵심입니다. **코드를 읽어야만 보이는 것들입니다.**

### 2-1. 복약 알림에 약 이름이 실려 나간다

`src/app/api/push/dispatch/route.ts`

```ts
const payload = JSON.stringify({
  title: "복약 시간입니다",
  body: `${reminder.medication_name}${dosage}`,   // ← 약 이름 + 용량
  ...
});
```

복용 중인 약 이름은 **질병을 직접 추론하게 하는 정보**입니다. 그런데 알림
기능의 데이터 흐름이 어느 문서에도 없습니다.

정확히 쓰자면 두 가지를 나눠야 합니다.

- **페이로드 내용**: Web Push 는 RFC 8291 에 따라 종단간 암호화되므로 푸시 서비스
  사업자(Google/Apple/Mozilla)는 약 이름을 **읽을 수 없습니다.** 이 점은 이용자에게
  유리한 사실이니 명시하는 편이 낫습니다.
- **그럼에도 노출되는 것**: ① 푸시 서비스는 "이 endpoint 에 언제 알림이 갔는지"를
  압니다. ② **잠금화면에 약 이름이 그대로 표시됩니다** — 옆 사람이 봅니다.

②는 처리방침 문제라기보다 **제품 안내 문제**입니다. 알림 설정 화면에 경고를
넣고, 약 이름을 숨기는 옵션을 제공하는 것이 바람직합니다. → §5 개선 제안

### 2-2. 수집 항목에 빠진 것들

문서의 "수집 항목"과 실제 스키마를 대조한 결과:

| 실제로 저장하는 것 | 위치 | 문서 기재 |
|---|---|---|
| `timezone` | `profiles` | ❌ |
| `weekly_exercise_goal_min` | `profiles` | ❌ |
| `user_agent` | `user_consents`, `push_subscriptions` | ❌ |
| 푸시 구독 정보(endpoint, 키) | `push_subscriptions` | ❌ |
| 사용자가 등록한 음식명 | `user_foods` | ❌ |

`user_agent` 는 접속 기기 정보이므로 수집 항목에 들어가야 합니다.
`user_foods` 의 음식명은 식습관·종교·질환을 추론할 여지가 있어 가볍게 볼 수 없습니다.

### 2-3. 식약처 API 호출이 문서에 없음

`src/lib/food/mfds.ts` — 음식 검색어가 공공데이터포털로 나갑니다.
**서버가 호출하므로 이용자 IP·식별자는 전달되지 않습니다.** 위험은 낮지만
"외부로 나가는 것이 있다"는 사실 자체는 적어야 합니다.

### 2-4. Anthropic 의 보유·파기 조건을 확인 없이 단정하고 있음

현재 문안:

> 보유 기간: 처리 완료 후 즉시 파기 (모델 학습에 이용되지 않음)

이건 **계약과 상대방 정책으로 확인해야 하는 사실**입니다. 확인 없이 단정한
고지는 부실 고지가 되고, 사실과 다르면 그 자체로 문제가 됩니다.

→ §4-3 에서 확인 항목으로 다룹니다.

### 2-5. 파기 절차·방법이 "즉시 파기" 한 줄

**근거**: 개인정보보호법 제21조, 제30조 제1항 제2호

실제 동작은 문서보다 훨씬 구체적입니다 (검증 완료):

- 탈퇴 시 `auth.users` 행 삭제 → `public` 스키마 16개 테이블이 cascade 로 삭제
- Storage 원본은 즉시 삭제하고, 실패에 대비해 `storage_cleanup_queue` 가 경로를
  잡아 두었다가 정리 배치가 지움
- 검진을 개별 삭제해도 그 검진에서 확정한 수치까지 함께 삭제 (트리거)

이 내용이 문서에 있으면 이용자 신뢰에도 도움이 되고 법정 기재사항도 충족합니다.

### 2-6. 안전성 확보조치 미기재

**근거**: 개인정보보호법 제29조, 제30조 제1항 제7호

실제로 구현되어 있는데 문서에 없습니다.

- 전 테이블 RLS 로 행 단위 격리 (`0002_rls_policies.sql`)
- 결과지 파일은 비공개 버킷 + 10분 만료 signed URL 로만 접근
- 접근 권한 최소화 (`user_timezone` 등 SECURITY DEFINER 함수의 실행 권한 회수)
- 전송 구간 암호화(HTTPS), 저장 시 암호화(Supabase 관리)

## 3. 🟡 보완

### 3-1. enum 주석과 실제 설정이 어긋남

`supabase/migrations/0001_initial_schema.sql`

```sql
'llm_processing',        -- 검진 결과지 외부 LLM 처리 동의 (필수)
```

주석은 "필수"인데 `0004` 에서 `is_required = false` 입니다. 실제 동작은
`false` 가 맞습니다 — 거부해도 수동 입력으로 서비스를 쓸 수 있으므로 선택
동의여야 합니다. **주석을 고쳐야 합니다.**

### 3-2. 만 14세 미만 아동 관련 조항 없음

**근거**: 개인정보보호법 제22조의2

건강 관리 서비스라 미성년 이용 가능성이 실재하는데 조항이 없습니다.
가입을 막을지, 법정대리인 동의를 받을지 정해야 합니다. → §4-4

### 3-3. 정보주체 권리 행사 방법이 추상적

"열람·정정·삭제를 요청할 수 있습니다"만 있고 **어떻게** 하는지가 없습니다.
실제로는 앱 안에서 대부분 가능합니다(기록 화면에서 열람·수정·삭제, 설정에서
동의 철회와 탈퇴). 그 경로를 적으면 됩니다. 처리 정지 요구와 대리인 행사
방법은 별도로 필요합니다.

### 3-4. 권익침해 구제방법 미기재

개인정보분쟁조정위원회, 개인정보침해신고센터, 대검찰청, 경찰청 연락처가
관행적으로 요구됩니다.

### 3-5. 처리방침 변경 고지 절차 없음

변경 시 최소 7일 전 공지 등의 절차가 있어야 합니다.

## 4. 최종 판단이 필요한 항목 (변호사 확인)

내가 결정할 수 없고, 결정에 따라 문서가 달라지는 것들입니다.

### 4-1. Supabase / Vercel 리전 → 국외 이전 해당 여부

리전이 국외(예: `ap-northeast-1` 도쿄, `us-east-1`)이면 **모든 개인정보가 상시
국외에 저장**되는 것이고, 국외 이전 고지·동의 대상이 됩니다.
서울 리전(`ap-northeast-2`)을 쓰면 이 문제가 상당히 단순해집니다.

**권고**: 가능하면 서울 리전. 민감정보를 다루는 서비스에서 국외 저장은
설명 부담이 계속 따라옵니다.

### 4-2. 민감정보 국외 이전의 적법 근거

검진 판독은 Anthropic(미국)을 쓰는 이상 국외 이전이 불가피합니다.
별도 동의로 해결할 것인지, 다른 근거를 쓸 것인지 판단이 필요합니다.
"선택 기능이고 거부해도 서비스 이용 가능"이라는 구조는 유리한 조건입니다.

### 4-3. Anthropic 과의 계약·정책 확인

- 상업적 이용 조건에서 API 입력 데이터가 모델 학습에 쓰이지 않는지
- 신뢰·안전 목적의 보관 기간이 실제로 얼마인지
- 개인정보 처리 부속 계약(DPA) 체결이 필요한지·가능한지
- 이전받는 자의 연락처(고지 항목)

확인 결과에 따라 §2-4 문안이 달라집니다. **확인 전에는 단정하지 말아야 합니다.**

### 4-4. 만 14세 미만 정책

가입 차단이 가장 단순합니다. 허용한다면 법정대리인 동의 절차를 구현해야
하고, 그건 코드 작업이 추가로 필요합니다.

### 4-5. 의료기기 해당성

코드는 판정을 하지 않도록 설계되어 있습니다 — 상태 라벨은 정상/주의/범위
밖/판정 기준 없음 4종뿐이고 병명이 없습니다(`src/lib/metrics/status.ts`).
식약처 「의료기기와 개인용 건강관리(웰니스) 제품 판단기준」상 웰니스 제품에
해당할 가능성이 높다고 봅니다.

다만 **검진 결과지 자동 판독**은 판단이 갈릴 수 있는 기능입니다. 판독은
"옮겨 적기"이지 "해석"이 아니고 사용자 확정을 거치지만, 식약처 사전 문의를
권합니다.

### 4-6. 동의 이력을 탈퇴 시 삭제하는 것이 맞는가

현재는 탈퇴하면 `user_consents` 도 cascade 로 삭제됩니다. 처리방침의
"탈퇴 즉시 전부 파기"와는 일치하지만, **적법하게 동의받았다는 사실을
입증할 수단이 사라집니다.**

파기 원칙과 입증 필요 사이의 트레이드오프입니다. 보존한다면 이용자 식별정보를
분리한 형태여야 하고, 그건 스키마 변경입니다.

## 5. 코드 개선 제안 (법무와 별개)

문서를 고치는 것만으로는 해결되지 않고 코드를 손대야 하는 것들입니다.

| 제안 | 이유 | 상태 |
|---|---|---|
| `0001` 의 `llm_processing` 주석 수정 | 주석 "필수" ↔ 실제 `is_required=false` | ✅ 완료 |
| 데이터 내보내기(다운로드) 기능 | 열람권 행사 수단이자 서비스 종료 시 반출 경로 | ✅ 완료 (§5-2 ②) |
| 만 14세 미만 가입 차단 | 약관에만 있고 코드에 없었음 | ✅ 완료 (§5-2 ①) |
| 복약 알림에서 약 이름 숨기기 옵션 | 잠금화면 노출 | ✅ 완료 — 기본값 숨김 |
| 처리방침 버전 이력 화면 | 이용자가 과거에 무엇에 동의했는지 확인할 수 있어야 함 | ✅ 완료 |

## 5-2. 2차 검토 — 새 초안이 코드와 맞는가

**2026-08-05 추가.** §1~3 은 *기존* 초안(`1.0-draft`)에 대한 검토였습니다.
그 지적을 반영해 `docs/legal/` 에 다시 쓴 초안을, 이번에는 **코드가 실제로
하는 일과 한 줄씩 대조**했습니다. 문서가 약속한 것을 코드가 지키지 않으면
그 자체가 허위 고지가 되기 때문입니다.

### 맞는 것 (확인 완료)

| 문서가 약속한 것 | 코드 |
|---|---|
| 결과지는 10분 만료 일회성 주소로만 열람 | `SIGNED_URL_TTL_SEC = 600` |
| 복약 "복용 목적"을 수집 | `medications.purpose` |
| 행 단위 격리 | RLS 정책 69개 (검증 완료) |
| 탈퇴 즉시 전부 파기 | 16개 테이블 cascade (검증 완료) |
| 검진 삭제 시 확정 수치도 삭제 | `checkups_delete_metrics` 트리거 |
| 판독 결과는 확인 전 반영되지 않음 | `confirm_checkup_extraction()` 만이 승격 경로 |
| 선택 동의는 설정에서 철회 | `updateOptionalConsent` |
| 필수 동의 철회는 계정 삭제로 처리 | 같은 함수가 필수 항목을 거부 |
| 상태 표시는 네 가지뿐 | `src/lib/metrics/status.ts` |
| 알림 내용은 종단간 암호화 | `web-push` (RFC 8291) |

### 어긋난 것 3건 — 이번에 맞췄습니다

**① 만 14세 미만 가입 차단이 코드에 없었다**

이용약관 제4조 ②에 "만 14세 미만은 가입할 수 없습니다"라고 썼는데,
**어디에도 연령 검사가 없었습니다.** 가입 시 나이를 묻지 않고, 프로필의
출생연도는 선택 입력이었습니다.

→ 동의 화면에 "태어난 해"를 필수로 추가하고, 화면과 서버 액션 양쪽에서
   검사합니다. 확인에 쓴 값은 프로필에 남겨 다음 단계에서 다시 묻지 않고,
   연령별 참고범위 판정에도 그대로 씁니다.

> 생년월일 전체가 아니라 **연도만** 받습니다. 만 나이를 정확히 계산하려면
> 생일이 필요하지만, 그것은 수집 최소화 원칙에 어긋납니다. 연도 차이로
> 판정하면 생일 전인 만 13세가 통과할 수 있다는 한계가 있습니다 —
> 변호사 확인이 필요한 지점입니다.

**② 데이터 내려받기가 없었다**

이용약관 제7조 ③은 "서비스 종료 시 데이터를 내려받을 수 있는 기간을
제공한다"고 약속하고, 처리방침 §7 은 열람권을 보장합니다. 그런데 화면에서
하나씩 보는 것 말고 전체를 받을 방법이 없었습니다.

→ `GET /api/export` 추가. RLS 를 우회하지 않는 클라이언트로 읽으므로
   `user_id` 조건을 빠뜨려 남의 데이터가 섞이는 사고가 구조적으로 일어나지
   않습니다. 설정 화면에 "내 데이터 내려받기"를 넣었습니다.
   결과지 원본 파일은 응답 크기 때문에 제외하고, 그 사실을 응답에 적습니다.

**③ 마케팅 동의가 없는 기능을 기술하고 있었다**

문서는 "이메일로 월 1회 이하 발송", "수신거부 링크"를 약속하는데
**발송 경로가 코드에 없습니다.** 동의 여부만 저장합니다.

→ 기능이 없으므로 구현하지 않고 **문서를 사실에 맞게 고쳤습니다.**
   문서 상단에 미구현임을 명시하고, 발송 기능을 만들 때까지 이 동의 항목을
   노출하지 않는 쪽을 권고했습니다. 쓰지 않을 동의를 미리 받아 두는 것은
   수집 최소화 원칙과도 맞지 않습니다.
