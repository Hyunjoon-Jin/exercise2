# 통합 건강관리 플랫폼 — 기획서

> 상태: 초안 (v0.1) · 작성일 2026-08-04
> 결정된 전제: 다중 사용자 서비스 / 반응형 웹 / MVP 6개 도메인(신체기록·수면·복약·식단·운동·건강검진) / 검진 결과 PDF·이미지 자동 판독

---

## 0. 범위에 대한 사전 의견

MVP로 정한 6개 도메인 + 검진 자동판독은 1차 릴리스로는 넓은 편입니다. 특히 **검진 자동판독(OCR/LLM)** 과 **복약 알림 인프라**는 각각 독립된 난이도를 가진 기능이라, 이 둘을 초반에 동시에 붙이면 나머지 기록 기능의 완성도가 희생될 가능성이 큽니다.

다만 요청하신 범위를 축소하지 않고, **전 범위를 계획에 포함하되 내부적으로 5개 단계(Phase)로 쪼개어** 순차 릴리스하는 방식으로 설계했습니다. 각 Phase는 그 자체로 사용 가능한 상태이므로, 중간에 일정 조정이 필요하면 Phase 단위로 판단하시면 됩니다.

## 1. 제품 정의

### 한 줄 정의
일상 로그(식단·운동·복약·수면·신체수치)와 연 단위 스냅샷(건강검진)을 **하나의 시간축**에서 함께 보는 개인 건강 데이터 허브.

### 차별점 — 왜 "통합형"인가
시중 앱은 대부분 단일 도메인에 특화되어 있습니다(식단 앱, 운동 앱, 복약 앱). 사용자는 데이터를 여러 앱에 흩뿌려두고, 정작 "작년 검진에서 공복혈당이 높게 나왔는데 그 이후 내 식단과 체중이 어떻게 변했나?"라는 가장 중요한 질문에는 답하지 못합니다.

**이 제품의 핵심 가치는 상관관계입니다.** 그러려면 서로 다른 출처의 수치가 같은 그래프에 올라가야 합니다 → 아래 §3의 통합 지표 체계가 이 제품의 기술적 핵심입니다.

### 핵심 사용자 시나리오

| 주기 | 행동 | 필요한 것 |
|---|---|---|
| 매일 | 아침 체중 입력, 식사 3회 기록, 복약 체크, 수면 기록 | **입력 마찰 최소화** — 3초 안에 끝나야 함 |
| 주 1회 | 주간 리포트 확인 (체중 추세, 복약 순응도, 운동 빈도, 칼로리 평균) | 자동 생성 |
| 연 1회 | 검진 결과지 업로드 → 자동 판독 → 확인 → 저장 | 판독 정확도 + 검수 UI |
| 수시 | "혈당 추세" 조회 → 자가측정 + 검진 수치가 한 그래프에 | **통합 지표 체계** |

## 3. 핵심 설계 결정 — 통합 지표 코드 체계

**이 문서에서 가장 중요한 결정입니다.**

신체기록의 "공복혈당"과 검진 결과지의 "공복혈당"은 사용자에게 같은 값입니다. 이 둘을 별도 테이블에 따로 저장하면 통합 그래프를 그릴 때마다 조인·정규화·단위변환을 매번 해야 하고, 지표가 늘어날 때마다 스키마가 바뀝니다.

### 해결: 단일 `health_metrics` 테이블 + 공통 지표 코드

```
health_metrics
├─ metric_code : 'GLUCOSE_FASTING' | 'WEIGHT' | 'BP_SYSTOLIC' | 'HDL' | ...
├─ value       : numeric
├─ unit        : 'mg/dL' | 'kg' | 'mmHg' | ...
├─ measured_at : timestamptz
└─ source      : 'self' | 'checkup' | 'device'
```

- 지표 정의(`metric_definitions`)는 별도 마스터 테이블: 코드, 표시명, 단위, 정상범위(성별/연령별), 카테고리
- 코드 체계는 **LOINC 일부를 차용하되 자체 코드로 단순화**. LOINC 전체를 도입하면 초기 복잡도가 과합니다. 대신 `loinc_code` 컬럼을 두어 향후 표준 연동 여지를 남깁니다.
- 신규 지표 추가 = 마스터 테이블에 행 하나 추가 (스키마 변경 없음)

### 이 결정의 효과
- "혈당 추세" 화면 = `WHERE metric_code='GLUCOSE_FASTING'` 한 방
- 자가측정/검진 구분은 `source`로 표시만 다르게(점 모양 등)
- 정상범위 표시 로직이 전 지표에 공통 적용

식단/운동/복약/수면은 구조가 다르므로 별도 테이블을 갖되, **파생 지표는 `health_metrics`에 함께 기록**합니다(예: 일일 총 칼로리 → `CALORIE_INTAKE_DAILY`, 수면시간 → `SLEEP_DURATION`). 그래야 "수면시간 vs 체중" 같은 교차 분석이 같은 쿼리 경로로 나옵니다.

## 4. 데이터 모델 (개요)

```
users ─┬─ profiles (생년, 성별, 키, 목표)
       ├─ consents (민감정보 동의 이력 — 필수)
       │
       ├─ health_metrics ◄────── metric_definitions (마스터)
       │     └ source: self | checkup | device
       │
       ├─ meals ─── meal_items ─── foods (식약처 DB 캐시)
       ├─ workouts ─── workout_sets
       ├─ sleep_records
       │
       ├─ medications ─── medication_schedules ─── medication_logs
       │
       └─ checkups ─┬─ checkup_documents (Storage 참조, 암호화)
                    └─ checkup_extractions (LLM 원본 추출 결과 + 검수 상태)
                          └─ 확정 시 health_metrics 로 insert
```

핵심 포인트:
- `checkup_extractions`는 **LLM이 뽑은 원본을 그대로 보존**합니다. 확정된 값만 `health_metrics`로 넘어갑니다. 판독 오류를 나중에 추적·재처리하기 위함입니다.
- 모든 사용자 데이터 테이블에 `user_id` + RLS(Row Level Security) 필수.

## 5. 기술 스택 (추천)

| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js (App Router) + TypeScript** | 서버 액션으로 API 레이어 최소화, PWA 전환 용이, Vercel 배포 |
| UI | **Tailwind CSS + shadcn/ui** | 반응형 우선, 컴포넌트 직접 소유 |
| 차트 | **Recharts** | 시계열 위주라 충분, 번들 부담 적음 |
| DB/인증/스토리지 | **Supabase (Postgres + Auth + Storage)** | **RLS로 행 단위 사용자 격리**가 다중 사용자 민감정보 서비스에 결정적. 검진 파일 스토리지까지 한 곳에서 해결 |
| 검진 판독 | **Claude API (`claude-opus-5`)** | 아래 §6 |
| 알림 | **Web Push (PWA) + Supabase pg_cron** | 복약 알림. iOS는 16.4+ 홈화면 추가 필요 (제약 있음, §9 리스크) |
| 배포 | **Vercel** | 이 세션에 Vercel/Supabase MCP 연동이 이미 있어 셋업이 빠름 |

> 참고: 이 세션 환경에 Supabase·Vercel·Netlify MCP가 연결되어 있어, 프로젝트 생성·마이그레이션·배포를 대화 중에 바로 진행할 수 있습니다.

## 6. 건강검진 자동판독 파이프라인

요청하신 "PDF/이미지 자동 판독"의 구체 설계입니다.

### 흐름

```
1. 업로드     사용자가 PDF 또는 사진을 업로드
                → Supabase Storage(비공개 버킷)에 저장
                → checkup_documents 레코드 생성

2. 추출       서버 액션/Edge Function에서 Claude API 호출
                - PDF: document 블록(base64 또는 Files API)으로 직접 전달
                  → 별도 OCR 엔진 불필요. 텍스트 PDF·스캔 PDF 모두 처리
                - 이미지: image 블록(base64/URL)
                - Structured Outputs로 JSON 스키마 강제
                → checkup_extractions에 원본 저장 (상태: pending_review)

3. 검수       사용자에게 추출 결과를 표 형태로 제시
                - 항목명 / 수치 / 단위 / 신뢰도
                - 원본 이미지·PDF를 나란히 표시하여 대조 가능
                - 사용자가 수정·삭제·확정
                → 자동 저장 금지. 반드시 사람의 확정을 거침

4. 반영       확정된 항목만 health_metrics 로 insert
                → source='checkup', measured_at=검진일
                → 자가측정 데이터와 같은 그래프에 즉시 합류
```

### 모델 선택

| 항목 | 결정 |
|---|---|
| 모델 | **`claude-opus-5`** — $5/$25 per MTok. 검진 결과지는 표·수치가 밀집한 문서라 판독 정확도가 곧 제품 신뢰도. 비용보다 정확도 우선. 연 1~2회 발생하는 이벤트라 사용자당 호출량 자체가 적음 |
| 대안 | 비용 최적화가 필요해지면 `claude-sonnet-5`($3/$15)로 A/B. 단 정확도 검증 후 |
| PDF 입력 | `document` 콘텐츠 블록 (base64 또는 Files API `file_id`). 요청당 32MB, 600페이지 제한 — 검진 결과지는 통상 2~10페이지라 여유 |
| 이미지 입력 | `image` 블록. Opus 5는 고해상도 비전 지원(장변 2576px) → 촬영본 판독에 유리 |
| 출력 강제 | **Structured Outputs** (`output_config.format` + JSON Schema). 파싱 실패·재시도 루프 자체가 불필요해짐 |
| 신뢰도 | 스키마에 항목별 `confidence` 필드를 포함시켜, 낮은 항목을 검수 UI에서 강조 |
| 인용 | ~~`citations: {enabled: true}`~~ — Structured Outputs 와 함께 쓸 수 없다(400). 대신 스키마에 `page_number` 를 두어 검수 UI 가 몇 쪽인지 표시한다 |

### 추출 스키마 (초안)

```jsonc
{
  "checkup_date": "2026-03-14",
  "institution": "○○병원 건강검진센터",
  "results": [
    {
      "raw_label": "공복혈당",         // 결과지에 적힌 그대로
      "metric_code": "GLUCOSE_FASTING", // 마스터 코드로 매핑
      "value": 102,
      "unit": "mg/dL",
      "reference_range": "70-99",
      "confidence": 0.96
    }
  ],
  "unmapped": []   // 코드 매핑 실패 항목 — 사용자가 수동 지정
}
```

`metric_code` 매핑은 **프롬프트에 마스터 코드 목록을 주입**하여 LLM이 직접 매핑하게 하고, 실패분은 `unmapped`로 빼서 사용자가 지정하도록 합니다. 이렇게 하면 병원마다 다른 항목명 표기(공복혈당/식전혈당/FBS)를 코드로 흡수할 수 있습니다.

### 비용 감각
검진 결과지 5페이지 기준 입력 ~10K 토큰, 출력 ~2K 토큰 → 회당 약 $0.10. 사용자당 연 1~2회이므로 총 비용은 무시할 수준입니다.

## 7. 보안 및 규제 — 다중 사용자 서비스의 필수 항목

건강정보는 **개인정보보호법상 민감정보**입니다. 다중 사용자 서비스로 결정된 이상 이 항목들은 선택이 아닙니다.

| 항목 | 내용 | 시점 |
|---|---|---|
| 민감정보 별도 동의 | 일반 개인정보 동의와 **분리된** 별도 동의 필수. 동의 이력을 `consents` 테이블에 보존 | Phase 0 |
| 행 단위 격리 | 모든 테이블에 RLS 정책. `auth.uid() = user_id` | Phase 0 |
| 파일 보호 | Storage 비공개 버킷 + signed URL(단기 만료). 검진 파일은 저장 시 암호화 | Phase 3 |
| 최소 수집 | 필요 없는 항목은 애초에 받지 않음 (주민번호 등 절대 수집 금지) | 전 구간 |
| 보존·파기 | 보존기간 명시, 회원 탈퇴 시 즉시 파기 절차 구현 | Phase 5 |
| 의료법 리스크 | **진단·처방으로 오인될 표현 금지.** 정상범위 표시는 가능하되 "정상/주의"까지, "당뇨 의심" 같은 판단 문구는 배제. 전 화면에 "참고용이며 의학적 판단은 의료진과 상담" 고지 | 전 구간 |
| LLM 데이터 취급 | 검진 데이터가 외부 API로 전송됨을 처리방침에 명시. Anthropic API는 기본적으로 학습에 사용되지 않음을 근거로 안내 | Phase 3 |
| 약관·처리방침 | 이용약관 + 개인정보 처리방침 (민감정보 처리 항목 포함) | Phase 5 (릴리스 전 필수) |

## 8. 단계별 로드맵

각 Phase는 종료 시점에 배포 가능한 상태입니다.

### Phase 0 — 기반 (약 1주)
- Next.js + Supabase 프로젝트 셋업, CI/배포 파이프라인
- 인증(이메일 + 소셜), 온보딩, **민감정보 동의 플로우**
- 전 테이블 스키마 + RLS 정책
- 앱 셸: 반응형 레이아웃, 네비게이션, 디자인 토큰
- **`metric_definitions` 마스터 데이터 구축** ← 이후 모든 Phase가 여기 의존

### Phase 1 — 기록 코어 (약 2주)
- 신체기록 CRUD + 추세 그래프
- 수면 기록
- 복약: 약 등록, 스케줄, 복용 체크, 순응도
- 복약 알림 인프라(Web Push + 스케줄러)
- **공통 기록 UI 패턴 확립** ← 식단/운동이 이 패턴을 재사용

### Phase 2 — 식단·운동 (약 2주)
- 식약처 식품영양성분 공공 API 연동 + 로컬 캐시
- 식단 기록: 검색 → 양 지정 → 저장, 최근/즐겨찾기로 마찰 감소
- 칼로리·탄단지 일일 집계 → `health_metrics`에 파생 기록
- 운동 기록 + 주간 목표

### Phase 3 — 검진 자동판독 (약 2주)
- 업로드 → Storage → 추출 파이프라인 (§6)
- Claude API 연동, 스키마·프롬프트 구축
- **검수 UI** (원본 대조 + 수정 + 확정) ← 이 Phase의 난이도 대부분이 여기
- 확정 → `health_metrics` 반영 → 통합 그래프 완성

### Phase 4 — 대시보드·리포트 (약 1주)
- 홈 대시보드: 오늘 요약, 주요 지표 카드
- 지표 통합 그래프 (자가측정 + 검진 동시 표시)
- 주간 자동 리포트

### Phase 5 — 릴리스 준비 (약 1주)
- PWA(홈화면 추가, 오프라인 기본 지원)
- 접근성(WCAG AA), 성능 최적화
- 약관·개인정보 처리방침, 탈퇴/파기 절차
- 부하 테스트, 모니터링

**총 예상: 약 9주** (1인 풀타임 기준, 검증 없는 러프 추정)

## 9. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **검진 판독 정확도** | 잘못된 수치가 저장되면 제품 신뢰도 붕괴 | 자동 저장 절대 금지 — 사용자 검수 필수. 항목별 confidence 노출. 초기 20~30건 수기 검증으로 정확도 측정 후 릴리스 |
| **식단 입력 마찰** | 3일 쓰고 이탈하는 주원인 | 최근 항목/즐겨찾기/"같은 식사 반복" 원터치. 정확도보다 지속성 우선 |
| **iOS 푸시 제약** | 복약 알림이 iOS Safari에서 홈화면 추가 없이는 안 됨 | 온보딩에서 홈화면 추가 유도. 장기적으로 네이티브 앱 검토 |
| **의료법 저촉** | 서비스 중단 리스크 | 진단성 표현 전면 배제, 고지 문구 상시 노출, 릴리스 전 법률 검토 권장 |
| **MVP 범위 과대** | 일정 지연 | Phase 단위 릴리스로 조기 검증. Phase 1~2만으로도 사용 가능한 제품 |
| **공공 API 의존** | 식약처 API 장애/스펙 변경 | 로컬 캐시 + 수동 입력 폴백 |

## 10. 다음 단계에서 결정이 필요한 항목

기획을 확정하기 전 답이 필요한 것들입니다. 지금 답이 없어도 Phase 0~1은 진행 가능합니다.

1. **음식 DB 소스** — 식약처 공공데이터포털 API를 쓸지, 자체 DB를 구축할지 (API 키 발급 필요)
2. **웨어러블 연동** — 애플 헬스/구글 핏/삼성 헬스 연동을 로드맵에 넣을지 (넣는다면 네이티브 앱이 사실상 필수)
3. **수익 모델** — 무료/프리미엄 구분이 있는지. 있다면 어떤 기능이 유료인지 (데이터 모델에 영향)
4. **운영 주체** — 개인 프로젝트인지 사업화인지. 사업화라면 사업자 등록·개인정보처리자 신고 등 절차가 추가됨
5. **팀 규모/일정** — 위 9주 추정의 기준을 조정해야 함
